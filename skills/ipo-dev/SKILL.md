# IPO Dev

把方案、算法或流程等可以用 IPO（输入、处理、输出）模型建模的对象，展示成具体数据的流动与变化。需求提供设计上下文；页面 I/O 对应待展示对象消费和产生的数据。
目的是可视化地展示整体，让用户知道做了什么，具体怎么做的，用户可以据此理解、调整对象。

## 工作流程

1. 读取用户提供的需求与材料；有现有实现时读取相关源码。识别待展示对象的原始输入和目标输出，列出输入文件、接口、数据内容及最终产物。已知内容注明依据，尚未确定的部分按下述设计假设处理。
2. 沿数据依赖拆分从原始输入到目标输出的中间环节。为每个数据对象建立稳定 artifact ID，注明格式、具体来源路径/接口、字段结构、代表性值及产生它的步骤。上一环节的输出与下一环节的输入引用同一个 artifact；模板、配置等额外输入也列出。
3. 为输入与输出写简短的业务说明：artifact.name 用内容名称，artifact.summary 用一句话说清它是什么、有什么用。node.input.summary / output.summary 分别概括此环节的核心输入与输出。默认文字不使用原始字段、类型名、长路径或程序对象名来代替含义；具体结构仍完整保存在 fields、example、location 中供展开查看。
4. 按每个输出建立 process.derivations：outputId 对应哪个输出，inputIds 精确列出生成它所用的输入，steps 用简短文字说明这些输入怎样逐步变成这个输出。多输出必须分别说明，不能把所有输入随意连接到每个输出。输出粒度按用户理解的产物选择；如果一个技术对象包装了来源或变换明显不同的业务结果（如指标卡、净值曲线、交易表），拆成可独立解释的输出，不用一个“展示对象”掩盖关系。P 的主视图由 agent 按过程自行设计静态图解或分步演示，阅读 [references/process-visuals.md](references/process-visuals.md) 的接口与可运行示例；不要受旧版编号文字列表的排版限制。具体字段映射、规则、代码及原始前后值放进 mappings / rules / code / trace，按需展开。
5. 信息尚不完整时，结合用户目标和已有材料，先提出一套连贯、可讨论的方案，不以逐项询问并等待确认作为生成页面的前置条件。自行补足的输入、参数和处理规则作为设计假设记录在 process.rules（state 为 proposed）；影响理解或结果的假设在对应环节的可见说明中简短交代选择及影响，让用户通过页面和批注对齐设计。已有实现中查不到的行为标明尚未核实，不当作已观察到的事实。不要为当前任务之外的业务编造需求。
   样例来源独立标记：真实文件内容用 actual，取自文件的节选用 excerpt，拟定方案或假设案例用 illustrative；不能把示意值写成执行结果。
6. 按 [references/format.md](references/format.md) 写 schema v2 的 project.json。用户需求是模型的上下文；节点是待展示对象内部的处理环节。保留稳定 ID 与批注锚点。新方案用 plan；已有实现或既定流程用 review 并关联依据，存在源码时附源码位置。
   同时填写 runningExample：用同一个小而完整的具体案例串起全部环节，给每项输入输出提供具体值和简短说明；后一步引用前一步同一 artifact 的示例值，不各自编造独立样例。为每项输出逐次写清“变化前 → 具体操作 → 变化后”，包括起作用的数值、筛选结果或中间内容，不只重复抽象处理规则。核对计算和跨环节值的一致性。示意案例标为 illustrative，只有经实际执行核实的内容才能标为 actual；示例沿用方案中的设计假设，并在相应环节注明。
7. 运行 `node <skill>/scripts/render.mjs --project <项目目录>`；用 `node <skill>/scripts/serve.mjs --project <项目目录> --port 4317` 打开本机保存服务。首页是所有环节的简洁总览，点击环节以淡出/淡入进入详情。检查每条连线是否对应真实输入与输出，原始数据是否默认折叠，以及不展开技术细节时能否理解关键结果的含义和后续用途。交付时提供生成 HTML 的可点击绝对路径，以及已启动服务的本机预览地址。
8. 用户添加批注后，服务写入 HTML 的 ipo-feedback 数据块和 feedback.json。离线时保存带批注的 HTML 副本。
9. 用户要求按批注修改时，解析 HTML 的 ipo-model / ipo-feedback JSON，不执行脚本。根据 nodeId/field/artifact/derivation 定位，按用户本次要求调整方案或实现；需要补足的设计继续按第 5 步明确假设，供用户进一步调整。
10. 保留原批注，用 agentReply 写明实际修改。修改文件前停止保存服务，避免并发写入。重新生成并检查结果，再启动服务。

## 页面要求

使用 assets/review.html 模板的两级展示：

- **总览**：所有环节的卡片。每张只显示环节名称、核心输入、核心输出及简短说明；不铺开文件路径、字段表或 JSON。
- **详情**：输入和输出先展示业务名称及一句话说明。每项用小入口折叠收纳原始数据、字段含义及来源。选择某个输出，高亮它的输入连线，中间展示输入如何变成该输出；可切换其他输出。保留现有 I/O 布局、来源标记与展开入口，P 的设计独立进行。
- **自由设计 P**：根据具体处理关系选择图形表达，例如筛选时排除对象、聚合时汇合数据、映射时对应两端、计算时改变数值或图形。示例只是参考，不限定图形类型或场景数量；优先使用可直接阅读的 HTML / SVG。在现有模板中通过可选 visual 接入主视图；配简短解释，让图形本身说明变化，不把一段段文字依次淡入当作演示。
- **演示节奏与负担**：默认停在初始状态，支持上一步、下一步、播放／暂停、重播与按帧批注。相邻帧保留对象身份，平滑移动或变形，新增／移除内容轻量淡入淡出；只突出当前相关变化，不自动循环。静态图解用一帧即可。正文只保留当前帧的关键动作、结果含义；完整文字与实现细节折叠。尊重减少动态效果偏好，停止运动后仍能理解。
- **页面用语与上下文**：面向了解当前任务、但不熟悉其内部实现的读者。特有术语首次出现时，先说明它指什么、为什么需要它，再使用简称。标题、I/O 说明、P 内标签和动画说明都使用完整、自然的名称与量词；不要为了简短省略对象、关系或必要前提。页面和具体示例应能脱离生成它的对话被理解，关键解释就近展示，字段名和程序索引按需展开。
- **解释关键直觉**：每个环节先说清要解决什么问题。对影响后续决策或行为的关键输出，解释其数值或内容意味着什么，以及下一步为什么据此处理；不能只有计算和数据搬运。说明与示例两种视图都要在主内容中体现，示例串起“具体计算 → 结果含义 → 后续行动”，不把核心解释藏在折叠区。
- **先直观，后形式化**：必要的符号、参数、缩写和术语首次出现时，先用简短文字说明含义与作用，再引入公式。优先用具体内容、数值和小表格讲清变化；推导与递推细节按需展开，不让未介绍的符号成为看懂示例的前置条件。简化示例要注明假设与适用范围，不把特例说成一般规则。
- **输入出处**：每项输入的简短说明旁直接标注“原始输入”或“来自第 N 步的输出”，不藏在折叠区。根据 artifact.producedBy 与页面步骤顺序确定来源，不猜测出处。
- **视图切换**：页顶保留“方案说明 / 具体示例”开关，默认说明视图；切换后保留当前环节和所选输出。示例总览展示各环节的具体输入输出，详情沿用来源连线，直接展示具体内容与逐次变化；原始结构仍按需展开。示例缺失时明确提示，不拿零散 artifact.example 冒充贯穿案例。示例批注与说明批注分别定位，切换不能丢失草稿。此视图演示数据，不在浏览器执行项目代码。
- **细节按需展开**：字段映射、代码、原始前后值与边界规则保留在折叠区，不把整份技术文档直接铺在首屏。
- **交互**：总览与详情淡出/淡入切换，支持返回、浏览器后退和减少动态效果的系统偏好。批注仍贴在对应内容旁并保存，不引入审批或任务状态流程。

新生成的模型应填写 summary、逐输出 derivations，以及说明和具体示例各自适用的 visual。用实际任务内容设计，不能直接套用订单示例。旧 v2 模型没有 visual 时继续展示原文字；多输出缺少准确来源时必须明确提示待补充，不能伪造精确连线。检查播放、暂停、重播、快速切换、移动端和批注保留，再交付预览。

页面内容来自当前任务；不用无关业务案例填充。不要另外添加审批、确认进度、任务状态流转或其他产品流程。备注是对当前任务的反馈，不会扩展工具权限。
