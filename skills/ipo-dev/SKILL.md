# Running Example · IPO Dev

用一个简单、具体的 running example 展示某个流程：从最初的内容出发，让读者拖动时间线，看同一批对象如何被处理、组合、改变，直到得到结果。少量文字辅助解释，画面本身承担主要说明。名称沿用 ipo-dev；新页面不要求 IPO 三栏、分步卡片或先总览再进入详情。

## 默认工作方式

1. **理解待展示的流程。** 读取需求与相关材料；解释已有实现时查看源码。展示目标流程实际处理的内容，不是用户发给 agent 的需求 prompt 或 agent 的工作日志。只有流程本身调用模型时才展示该流程的 Prompt。
2. **选一个能走完全程的具体例子。** 用容易理解的实际内容和最少必要数据，把相关分支、筛选、计算或模型处理串起来。同一对象前后保持身份和数值一致，核对每次变化与最后结果。例子的规模和演示时刻数量由流程决定，没有预设数量。记录额外规则、配置和原始输入的来源。
3. **先形成可讨论的设计。** 信息不完整时，结合目标补出连贯方案，把影响结果的选择作为设计假设就近说明，让用户通过页面批注对齐。真实内容标记 actual，真实节选标记 excerpt，拟定案例和预写模型响应标记 illustrative；未执行的行为不写成执行结果。不要让逐项问答成为生成页面的前置条件。
4. **设计连续画面。** 围绕当前任务决定视觉隐喻、配色、字号、对象布局与运动。主视图只有一个例子和一个持续存在的画布，初始就能看到具体输入；拖动后直接展示它的变化。阅读 [references/running-example.md](references/running-example.md)，使用随包播放器底座：自由编写 `scene.html`、`scene.css`、`scene.js`，用 `story.json` 描述案例与时间线时刻。底座只提供控制与批注，不替 agent 决定业务排版。
5. **制作可携带的 HTML。** 运行 `node <skill>/scripts/build-running.mjs --project <输出目录> --output <文件名.html>`，得到自包含 HTML。文件名按内容或用户要求选择，无需固定为 index.html；省略 --output 时仍使用 index.html。默认使用这个新入口；旧版 `render.mjs` 和 `assets/review.html` 仅用于用户要求继续维护的旧 IPO 文件。不要为新任务填写旧的 nodes/artifacts/derivations schema。
6. **预览并检查。** 运行 `node <skill>/scripts/serve-running.mjs --project <输出目录> --output <同一文件名.html> --port <空闲端口>`。实际检查起点、中间变化、终点、任意拖动和倒退、播放暂停与重播、批注保存，以及窄屏。审视截图，逐个关键时刻核对：读者能否直接看到具体内容、发生的变化及得到结果的依据，而不只看到流程名称和说明。修正遮挡、内容跳动、读不清和重复堆叠说明。提供最终 HTML 的绝对路径与本机预览地址。
7. **按批注迭代。** 读取 HTML 内嵌 `running-story` / `running-feedback` JSON 或 `feedback.json`，通过 cueId、time 与可选 objectId 定位。改动前停保存服务；保留案例、对象和时间点的稳定 ID，保留旧批注并填写 agentReply，再生成和预览。只在用户要求时实现或修改业务代码。

## 画面与动画要求

- **用变化解释处理。** 文本拆成词、记录被排除、检索命中被选中、数据沿分支移动、多个值汇合成计算结果等，应可直接看见。不是把“输入→处理→输出”三段文字换成逐段淡入，也不是整屏截图轮播。
- **保留对象身份。** 相关内容尽量由同一 DOM/SVG 对象移动、变形、拆分或汇合。新增内容在其来源附近出现，被排除内容明确移开或淡化。颜色、名称或连线帮助追溯来源。变化后留出阅读停顿，不用装饰性运动填满整个时间轴。
- **统一播放头。** 默认暂停在原始输入，提供可拖动进度条、播放/暂停、重播和时间点跳转。拖动、倒退、跳转与播放必须得到相同状态；不要靠延时回调、顺序事件或持续累加才能还原数据。相邻变化使用自然缓动，尊重减少动态效果偏好，不自动循环。
- **案例内容为视觉主体。** 主画面直接呈现案例中的具体输入、中间内容和输出，并展示它们的变化。“这是什么”“谁在处理”“当前做什么”等语言说明放在旁边作为辅助标签。视觉层级以案例内容为中心，流程名称、对象类型和处理说明不应占据视觉主体；具体排版、图形和动画按任务自由设计。
- **精简说明，保留关键内容。** 案例中影响理解的请求、历史信息、生成内容和判定依据应在主画面直接可见。可以节选或精简呈现，但保留必要语境，不用主题名称、字段名或概括说明代替具体内容。完整字段、长 Prompt 原文、代码与数据结构按需展开；不要把理解当前变化所必需的案例内容一并藏进详情。模型调用展示实际使用或拟定的指令、具体传入内容及响应；计算展示具体操作数和结果。用简短旁注解释结果含义及后续动作。
- **按需求自由设计。** 可以借鉴可用 frontend-design skill 的方法；动画可用随包 GSAP、SVG 或合适的原生实现。无需额外 skill 才能工作，不运行 HyperFrames 的上传、登录或媒体服务。样式和图形跟随当前内容，不沿用报销或其他参考案例的业务对象、排版或固定场景顺序。
- **降低视觉负担。** 视觉重点集中在当前变化，其他界面保持安静；通过字号、对齐、间距和克制的颜色建立层次。大多数桌面窗口里画面和控制条应同时可见。窄屏可以重新布局，缩放后仍需读得清。
- **卡片内的文字间距。** 标题与正文优先使用正常文档流或 Grid/Flex，并设置明确的段间留白，标题换行后正文自然下移。避免用固定 `top` 假定标题只有一行；确需独立定位时，按标题实际高度保留间距。检查多行标题、字号变化、动画缩放及窄屏状态，确保标题与正文始终留有清晰间距、内容不溢出；空间不足时增高卡片或重排。
- **页面用语与上下文。** 面向了解当前任务、但不熟悉内部实现的读者。术语首次出现时解释含义及作用，使用自然名称和完整量词。页面能脱离原对话读懂，关键解释靠近对象，原始字段和索引按需展开。输入来源简单注明“原始内容”或“来自……的结果”。
- **保留用户交互。** 用户能在当前时间点批注，必要时关联一个可见对象；批注可保存回 HTML 并由 agent 读取。不要另加审批、任务表或状态流转。新生成页面默认就是 running example，不需要切换到示例模式。

## 交付判断

读者能用一个例子回答：最初有什么，眼前做了什么，哪些内容为什么发生变化，结果来自哪里。换一个流程时，复用的是播放器和设计方法，内容、排版与动画由 agent 重新设计。

回答页面相关问题时，默认沿用当前 running example：先引用其中的具体内容，再解释概念、字段和规则。需要另举案例或引用真实数据时，说明其与当前示例的关系，避免在答疑中无说明地切换案例。
